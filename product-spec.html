TechNomad Virtual System

A complete, developer-ready specification for a minimal, boringly reliable personal operating system that reduces cognitive load through voice-first, factual task capture and recall. The AI behaves strictly as a clerk (transcribe, read back, summarise, remind) - no invention or speculation.

1) Executive Summary

Technomad is a single-user, voice-first cross-platform app that opens to a zero-friction dashboard showing only date, time, weekday, and a short status line (e.g., "You have 3 tasks today"). No feeds, no dopamine traps. Core is a plain-text task system with optional notes and a binary status (To-do / Done). AI is constrained to clerical operations to avoid hallucinations and cognitive overload. Success is proven when the system is used by its owner for 14 consecutive days.

2) Goals & Non-Goals

2.1 Goals

  • Reduce cognitive load; compensate for dyslexia, memory gaps, and time-blindness via predictable, low-stimulus workflows.
  • Voice-first capture with dependable transcription and immediate read-back.
  • Boring reliability over features; minimal scope, maximal stability.
  • Four clerical AI functions only: transcribe, read back, summarise existing text, remind.
  • Proof, not polish: measurable success = "I used my own system for 14 days."

2.2 Non-Goals (V1)

  • No priorities, tags, labels, colours, boards, gamification, or social features.
  • No creative generation, ideation, extrapolation, or coaching by AI. The AI is not a friend; it is a clerk.
  • No multi-user collaboration, shared workspaces, or admin panels.
  • No complex calendar integrations (beyond a simple "today count" derived from tasks).

3) Users & Success Metrics

3.1 Primary User

A solo user who needs reliable, predictable, factual assistance; values low cognitive friction; experiences dyslexia/time-blindness/memory gaps; prefers voice over typing.

3.2 Success Metrics (V1)

  • Adoption: App launched on >= 12 of 14 consecutive days.
  • Completion: >= 1 task marked "Done" on >= 10 of 14 days.
  • Friction: Average capture-to-task latency (start speaking -> task saved) <= 7 seconds.
  • Stability: Zero data loss incidents; crash rate < 0.5% of sessions.
  • Qualitative: User self-report: "My brain feels calmer while working." (weekly check-in)

The headline proof metric originates from your plan: "I used my own system for 14 days."

4) Product Scope (V1)

4.1 Dashboard (Login Landing)

  • Elements: Date, Time, Day of week, Status line ("You have N tasks today" / "No tasks logged" / "Last activity: HH:mm yesterday").
  • No notifications feed, badges, or external content.

4.2 Tasks

  • Fields: title (required), note (optional), status in {todo, done}. Nothing else.
  • Storage: Plain text representation with durable persistence.
  • Views:
    • Today (default): count + list of incomplete tasks created or due "today" (simple date field; no recurring logic in V1).
    • All: reverse-chronological by created date.
  • Actions: Add (voice/text), Mark done/undo, Edit title/note, Delete.

4.3 Voice & AI (Clerk-Only)

  • Allowed behaviours: Transcribe voice to text; Read back tasks; Summarise existing notes into shorter bullet points on request; Schedule simple reminders (local device notifications only).
  • Prohibited: Guessing, inventing, extrapolating, therapy, or "friend" persona. If unsure -> "I don't know."

5) Platform & Architecture

5.1 Cross-Platform Choice

Primary framework: Flutter (single codebase -> iOS, Android, macOS, Windows, Linux, Web). Rationale: mature multi-platform targets, strong accessibility support, excellent performance, offline-first patterns, consistent UI fidelity, robust plugin ecosystem (mic access, local DB, TTS).

Alternative (if needed later): React Native (mobile) + Electron/Tauri (desktop). Not used in V1 to avoid multi-repo complexity.

5.2 High-Level Architecture

[ UI (Flutter) ]
     |
[ Application Layer ]
     |-- Command handlers (AddTask, MarkDone, ReadBack, SummariseNote)
     |-- Policy guards (AI Clerk Rules)
     |
[ Data Layer ]
     |-- Local DB (SQLite via Drift)  <-- source of truth
     |-- Optional Sync Adapter (phase-gated; disabled by default)
     |
[ Device Services ]
     |-- Microphone, TTS, Local Notifications
     |
[ AI Services ]
     |-- STT: Azure Speech-to-Text (online)
     |-- TTS: Azure Speech (online) or on-device TTS where available
     |-- Summarisation: Azure OpenAI (GPT-4o-mini or equivalent), "summarise only"

Local-first by default; syncing can be added later as a separate phase. This matches your "stick to walk with" principle.

6) Functional Requirements

6.1 Authentication & Session

  • Single user: email + password or passkey (platform native).
  • Stay signed in until explicit logout.
  • No social login in V1.

6.2 Dashboard

  • Show Date / Time / Weekday / Status line on launch.
  • Status line rules:
    • If any todo with createdOn == today: "You have N tasks today."
    • Else if no tasks exist: "No tasks logged."
    • Else: "Last activity: {relative time}."

These strings reflect your plan for the MVP dashboard.

6.3 Task Management

  • Create (voice): Press/hold mic -> capture audio -> transcribe -> preview text -> confirm to save.
  • Create (text): Text field + Save.
  • Edit: Title and note.
  • Status: Toggle todo/done.
  • Delete: Hard delete (local DB).
  • Read Back: Select tasks -> device reads aloud via TTS.
  • Summarise note: On a task's note, optional "Summarise" produces a shorter version without adding new ideas.

6.4 Reminders (Local-Only)

  • Optional per task: time-based local notification.
  • No recurrence or snooze storms (V1). Keep it calm.

6.5 AI Behaviour (Enforced Rules)

  • If confidence < threshold or missing context -> reply "I don't know."
  • Disallow prompts that request ideation, opinions, or creative writing.
  • Summaries must be extractive or constrained abstractive of existing text only.
  • The assistant refers to itself only as a clerk; no social language.

These constraints codify the rules you set: "not creative... does not invent... reflects, records, reminds, and organises."

7) Non-Functional Requirements

  • Reliability: 99.5% crash-free sessions; no silent data loss.
  • Performance:
    • Cold start -> dashboard ready <= 2.5 s on mid-tier Android.
    • Voice capture to task saved <= 7 s median on 10 Mbps connection.
  • Security:
    • All network calls over TLS 1.2+.
    • Local DB encrypted at rest (SQLCipher via Drift).
    • API keys stored securely (platform keystore/keychain).
  • Privacy:
    • No analytics PII; opt-in diagnostics only.
    • Audio sent to cloud STT only for transcription; not stored server-side (provider setting).
  • Accessibility:
    • Full screen-reader labels; minimum 4.5:1 contrast; scalable text; large tap targets.
  • Internationalisation: English (en-GB) first; string externalisation.
  • Offline: Full read/write to local DB; queued sync (if enabled later).
  • Calm Design: No red badges, no animated distractions, no social proof patterns.

  • Last Activity: max of createdAt or completedAt.

9) API & Integrations (V1)

Architecture stance: Operate fully local by default. Integrations are thin and clerical.

9.1 Speech-to-Text (STT)

  • Provider: Azure Cognitive Services - Speech to Text.
  • Usage: Short utterances (<= 30s).
  • Output: transcript text + confidence score.
  • Policy: Do not store audio server-side; discard after transcription.

9.2 Text-to-Speech (TTS)

  • Provider: Azure Speech.
  • Voices: Natural, low-emotion voice; consistent rate/pitch.

9.3 Summarisation (Extractive/Constrained)

  • Provider: Azure OpenAI (GPT-4o-mini or comparable).
  • System prompt (fixed):
ROLE: Clerk.
You only summarise existing user text into shorter, clearer phrasing.
Never invent, guess, or add new information.
If inputs are insufficient, reply: "I don't know."

(Encodes your AI-as-Clerk doctrine.)

10) UX Specification

10.1 Visual Style

  • Monochrome + one accent (accessible contrast).
  • Generous line spacing, large type (min 16sp), high legibility.
  • Single primary button per view (keep choices obvious).

10.2 Key Screens

Dashboard

  • Top: large Date / Time / Weekday.
  • Centre: Status line.
  • Bottom: Mic button (hold-to-capture) + "Add text task".

Task List (Today)

  • Simple list with checkboxes; tap to toggle done; long-press to read back.
  • FAB: "Add task".

Task Detail

  • Title, note, status toggle, optional reminder time.
  • Button: "Summarise note" (AI).

Settings

  • Voice speed/volume; Accessibility font size; Opt-in diagnostics; Data export (.json).

10.3 Voice Capture Flow

  1. Hold mic -> waveform animates -> release to stop.
  2. Show transcript preview -> Confirm -> Task saved -> Snackbar: "Saved".
  3. On low confidence: show "I'm not sure I heard that - try again?"

11) Acceptance Criteria (Samples)

  • Dashboard shows date/time/weekday and status line exactly as spec'd; no other dynamic elements.
  • Create task (voice): From press to "Saved" <= 7 s median under 10 Mbps.
  • AI: Any prompt that asks for ideation produces "I don't know."
  • Summarise: Output contains only concepts present in input; 0% hallucinated entities in test suite.
  • Data safety: Force-quit during save does not corrupt DB (verified via property tests).

12) Telemetry & Logging (Opt-In)

  • Anonymous: session start/stop, crashes, latency buckets (STT end-to-save).
  • Never capture content of tasks or transcripts.
  • Error logs: local ring buffer; user may export for support.

13) Risks & Mitigations

  • STT accuracy variability -> Provide quick "edit before save"; store original transcript for 5 minutes locally to allow undo; fallback to text entry.
  • Cognitive overload creep -> Governance check before adding any field/feature; "No tags/priorities" policy locked in tests.
  • Scope drift -> Milestone gate: ship after V1 features only; anything else -> backlog.
  • Cloud dependency -> Offline read/write default; summaries optional; STT can defer to manual entry if offline.

14) Security, Privacy, Compliance

  • Encryption: At rest (SQLCipher), in transit (TLS 1.2+).
  • Secrets: Platform secure storage (Keychain/Keystore).
  • Data retention: All data resides locally; optional encrypted cloud backup (Phase 2).
  • User control: Export all data to JSON; delete all data (local wipe).
  • Privacy by design: No third-party analytics by default.

15) Testing Strategy

  • Unit tests: Data model, command handlers, AI policy guards.
  • Integration tests: Voice flow; save/edit/delete; reminder fire.
  • Property tests: DB integrity during interruption.
  • Accessibility tests: Screen reader, colour contrast, focus order.
  • Manual scripts: "14-Day Proof" script (daily launch, add >= 1 task, mark >= 1 done).

16) Release Plan (Milestones)

  • M0 - Foundations: Project scaffold, local DB, clean dashboard shell.
  • M1 - Tasks (Text): Create/edit/toggle/delete; Today view; Status line.
  • M2 - Voice: Mic capture -> STT -> save flow; read-back via TTS.
  • M3 - AI Summarise (optional): Constrained summaries for notes.
  • M4 - Reminders: Local notifications.
  • M5 - Stability & Proof: Fix bugs, run the 14-day proof.

17) Definition of Done (V1)

  • Meets all acceptance criteria; passes stability thresholds.
  • Used >= 12 of 14 days with >= 10 task completions.
  • No data loss incidents; crash-free sessions >= 99.5%.
  • The AI never produces invented content across the test suite.
  • App bundle signed and deployable to TestFlight/Internal testing tracks plus desktop installers.

18) Appendices

A) AI Policy Contract (Embed verbatim)

"This system is not creative.

It does not invent.

It reflects, records, reminds, and organises."

If it doesn't know, it says "I don't know."

Allowed: Transcribe, Read back, Summarise existing text, Remind.

Forbidden: Guessing, extrapolating, inventing, therapy, or social persona.

B) Out-of-Scope (Hold the line)

  • Tags, priorities, categories, labels, colours.
  • Complex scheduling/recurrence, calendar sync, email integration.
  • Collaboration, accounts/teams, sharing.
  • Any AI beyond the clerk role.
